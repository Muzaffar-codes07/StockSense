## 1. Executive Summary

- **Maturity: mid-build, surprisingly complete.** All four domains have real, working code — not stubs. This is well past scaffold.
- **Original requirements ≈ 85–90% implemented** (backend stronger than frontend). The gaps are integrity, security, and one fake screen — not missing features.
- **Role 1 (me): ~95% of mandatory scope done** (schema, migration, ledger, auth, warehouses, meta). Remaining Role-1 work is now mostly *hardening + stewardship*, not feature-writing.
- **Biggest strength: the ledger.** `postMove()` is the sole stock writer, on-hand is derived, quantities are `Decimal(18,3)`, and outgoing moves are serialized per (product,location) with a `pg_advisory_xact_lock`. No code path mutates stock directly. This is a genuine, defensible differentiator.
- **CRITICAL blocker #1 — double-post:** every `validate()` reads its "already-done" guard *before* the transaction and there's **no `UNIQUE(docType,docId)` on StockMove**, so concurrent (or racing) validations can post the ledger twice. (`receipts.service.ts:182-184` vs `:200`; migration `StockMove_docType_docId_idx` is a plain index.)
- **CRITICAL blocker #2 — auth has no rate limiting** anywhere; the OTP 5-attempt cap is bypassable by re-requesting codes, and login is stuffable (`auth.controller.ts`, no throttler).
- **HIGH — the dashboard is fake.** The routed `Dashboard.tsx` renders hardcoded numbers (124/5/3/8/2) and calls two endpoints that don't exist (`/products/summary`, `/operations/summary`); the *real* KPI endpoints + hooks exist but are dead code (`Dashboard.tsx:14-28`, `features/stock/LowStockCard.tsx`).
- **HIGH — `PATCH …/:id {status:'DONE'}` bypasses the ledger** entirely (update DTOs expose `status`, no guard): a doc can be DONE with zero moves posted (`receipts.dto.ts:48`, `receipts.service.ts:141`).
- **HIGH — OTP code is logged in plaintext in production** (`auth.service.ts:84`); no `JWT_SECRET` startup check; wide-open CORS; **no authorization/RBAC** (any logged-in user can do anything).
- **MEDIUM — `CreateAdjustmentModal` reads on-hand from a non-existent `/inventory` route** → "Recorded" silently defaults to 0 → wrong diffs (`CreateAdjustmentModal.tsx:59`).
- **Tests are good where they exist** (48 unit + 14 db-integration incl. the 77 flow, per-location split, oversell, concurrency, rollback) but **have zero frontend tests and no unauthorized / invalid-FK / HTTP-level coverage.**
- **Docs drift:** PHASE-0 test counts stale (says 7/7, 8/8 — actually 8 ledger unit, 14 db); dashboard "real numbers" DoD false; OTP doc says "stubbed" (it's implemented).
- **Phase 0: Gate A genuinely re-verified at `c18b871` today** (migration applies, 14/14 db tests). **Gate B (team schema sign-off) is still not done.**
- **Are we ready to add standout features? Not yet** — fix the two CRITICALs + the dashboard first (small, high-value). Then the ledger makes several standout features cheap.

## 4. Current Database Model

**Plain English:** Users (argon2) own hashed `PasswordResetOtp` rows. Warehouses contain self-nesting typed Locations. Products (unique SKU, `uom`, `unitCost Decimal(12,2)`, `isActive` archive flag, optional Category, one `ReorderRule`). **All stock is the append-only `StockMove` ledger** (product, optional from/to location, positive `qty Decimal(18,3)`, `moveType`, `docType`/`docId` provenance, `createdBy`); on-hand is **derived**, never stored. Four operation documents (Receipt/Delivery/Transfer/Adjustment) with `DocStatus` headers + line children; validating posts moves. Partners = suppliers/customers.

- **Enums:** `LocationType(STOCK,PRODUCTION,RACK,TRANSIT)`, `PartnerType`, `MoveType(RECEIPT,DELIVERY,INTERNAL,ADJUSTMENT)`, `DocStatus(DRAFT,WAITING,READY,DONE,CANCELED)`.
- **View:** `stock_quant(product_id, location_id, qty)` — hand-written SQL in the migration (`migration.sql:316-324`), **not modeled by Prisma** (drift risk on future StockMove column changes).
- **Unique:** `User.email`, `Category.name`, `Product.sku`, `ReorderRule.productId`.
- **Indexes:** StockMove `(productId,toLocationId)`, `(productId,fromLocationId)`, `(fromLocationId)`, `(toLocationId)`, `(docType,docId)` — not internally redundant. `Location(warehouseId)`, `Product(categoryId)`, `PasswordResetOtp(userId)`.
- **FK onDelete:** ledger-safe — `StockMove.productId` RESTRICT (why products archive, not delete), locations SET NULL; line tables CASCADE to headers, RESTRICT to product; partner SET NULL.

**DB issues:** (MEDIUM) **no indexes on operation line-table FKs** — esp. `DeliveryLine.productId`, scanned by the reserved/free-to-use CTE every stock read; (MEDIUM) **no DB CHECK for `qty>0`** or `COALESCE(from,to) IS NOT NULL` (integrity is app-only); (MEDIUM) **no `UNIQUE(docType,docId)` on StockMove** (enables double-post); (LOW) sparse timestamps; SKU case-insensitivity is app-only; `maxQty>=minQty` app-only.

## 8. Critical Technical Risks (ranked)

**CRITICAL**
1. **Double-post / oversell via validate() TOCTOU.** Status guard read before the tx (`receipts/deliveries/transfers/adjustments .service.ts` guard `~:182` vs post `~:200`); **no `UNIQUE(docType,docId)`**. Two racing validates both post. Incoming (receipt / +adjustment) has no advisory lock → doubles unconditionally; outgoing serializes on the lock but still double-posts if stock allows. Confirmed: `StockMove_docType_docId_idx` is a plain index.
2. **No auth rate limiting.** Credential stuffing on login; OTP re-request loop defeats the 5-attempt cap and can DoS a victim's reset. No `@nestjs/throttler`.

**HIGH**
3. **PATCH `…/:id {status:'DONE'}` skips the ledger** — update DTOs expose `status`, `update()` writes it unguarded (`*.dto.ts` status field; `*.service.ts:~141`). DONE with zero moves; later `validate()` refuses.
4. **OTP plaintext in prod logs** (`auth.service.ts:84`, unconditional).
5. **No `JWT_SECRET` presence/startup validation**; `JwtModule.register({})` empty; secret read per-call from env.
6. **CORS `origin:true, credentials:true`** (`main.ts:10`) — reflects any origin (mitigated by Bearer, not cookies).
7. **No authorization/RBAC** — any authenticated user can mutate anything.
8. **Stale adjustment diff** — validate posts the diff frozen at create, not re-snapshotted (`adjustments.service.ts:232`).

**MEDIUM**
9. Missing FK indexes on line tables (esp. `DeliveryLine.productId`, hit by every stock read).
10. No DB CHECK for `qty>0` / from-or-to presence; `stock_quant` view outside Prisma (drift).
11. `cancel()` cannot reverse a validated document (no compensating move) — a bad/duplicated post is uncorrectable except via a new adjustment.
12. Frontend has no auth guard; adjustment modal reads dead `/inventory` route → wrong "recorded".
13. Signup email enumeration; OTP request timing side-channel.

**Concurrency answer (the "10 units, A wants 8, B wants 8" scenario), traced:** For **outgoing** moves both requests enter a tx and contend on `pg_advisory_xact_lock(product:location)`. One wins the lock, reads on-hand=10, writes −8 (→2), commits, releases. The second then acquires the lock, reads on-hand=2, sees 2<8, throws `BadRequestException("Not enough stock…")`. **So a single-line oversell across two requests is correctly prevented today.** BUT this only protects the *stock* invariant — it does **not** prevent the same *document* being validated twice (no doc-level guard inside the lock/tx), and **incoming** moves take no lock at all. The db-spec `stock.db-spec.ts:57-64` confirms exactly-one-wins for two concurrent deliveries.
